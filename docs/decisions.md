# Decisions

One line each, why over what. This supersedes the previous (reservation-site)
version of this doc — that build was replaced entirely per the new brief.

## Schema + route-skeleton pass (Supabase backend, expanded IA)

### Existing project reconciliation

- **Found a pre-existing, non-fresh Supabase project ("petshop", id `pytkeurgdbhekyppfblh`) with real data** (4 profiles, 2 stores, 6 pets, 1 reservation, 1 wishlist row) instead of the fresh project the brief assumes. Asked the user how to handle it rather than guessing; they said check each table against the new spec, keep+extend what matches, wipe what doesn't. What follows is that table-by-table call:
  - **`stores`→`shops`, `pets`, `reservations`, `wishlists`: kept and altered/extended in place** (renamed columns, added missing columns, converted text+CHECK status columns to real enums, migrated `wishlists.pet_id` into the new polymorphic `item_type`/`item_id` shape). All existing rows survived.
  - **`profiles`: kept.** Renamed `full_name`→`name`, added `phone`/`email`, converted `role` text+CHECK (which didn't even allow `'admin'`) to a proper `user_role` enum, backfilling existing `'store_owner'` rows to `'shop_owner'` and `email` from `auth.users`.
  - **`payment_attempts`: wiped (dropped).** Zero rows, not part of the new 13-table spec, and its `confirmed` boolean tracks actual payment confirmation — directly conflicting with this project's established "no payment provider, nothing charged online" boundary.
  - **`create_reservation_atomic()` and `expire_pending_reservations()`: dropped, not adapted.** Both are reservation *workflow logic* — exactly what this pass is scoped to defer ("don't build... cart logic... yet") — and both are irreconcilably tied to `payment_attempts` / the pre-order-model `reservations` shape. Rebuilding them against the new `orders`-centric model is next-pass work.
  - **`handle_new_user()` (the `auth.users` signup trigger): kept and adapted**, not dropped — unlike the two functions above, this is schema/auth plumbing (profiles would never populate on signup without it), not business logic.
  - **Backfilled one `orders` row for the pre-existing reservation** (`order_type='pet_reservation'`, `payment_type='deposit'`) so `reservations.order_id` could be made `NOT NULL` without losing the row. That backfilled order has no corresponding `order_items` row (the old schema had no concept of one) — a shop owner's "orders containing their items" view won't surface that one legacy order. Accepted as a minor one-time gap rather than fabricating a price-bearing line item for it.
  - **Two indexes I didn't know about until a migration failed** (`reservations_one_active_per_pet` covering `pending`+`confirmed`, `reservations_expires_idx`) already existed from the original schema and were smarter than what I'd have written blind (I'd only considered `pending` as "active"). Dropped, recreated with the enum type, kept their original semantics.

### Enums inferred where the brief didn't give explicit values

The brief spelled out enum values for `pets.status`, `products.category`, `orders.order_type`, `orders.payment_type`, and `order_items`/`wishlists.item_type`. It left `shops.status` (given via the roles table's "approve or suspend" instead), `products.status`, `orders.status`, `reservations.status`, `gifts.delivery_status`, and `support_tickets.status` unspecified. Resolved as:
- `shop_status`: pending / approved / suspended (from the roles table's admin capability).
- `product_status`: available / unavailable.
- `order_status`: pending / paid / fulfilled / cancelled.
- `reservation_status`: pending / confirmed / expired / cancelled — **kept exactly the existing project's set** rather than inventing my own (its `expire_pending_reservations()` function and existing check constraint already used this exact set).
- `gift_delivery_status`: pending / sent / delivered.
- `support_ticket_status`: open / in_progress / resolved / closed.

### Structural judgment calls

- **`order_items.item_id` and `wishlists.item_id` have no FK.** Postgres can't express a conditional foreign key across two different target tables (pets vs. products) for a polymorphic column — this is a genuine "can't be expressed as specified" case, not something I silently worked around. The brief's own notes column already calls `order_items` "polymorphic on item_type," so this was anticipated, not a gap I'm introducing. Integrity for `item_id` is enforced at the application layer in the next pass.
- **`catalog_item_type` (pet/product) is one shared enum**, used by both `order_items.item_type` and `wishlists.item_type`, rather than two separately-named identical enums.
- **Added a `unique(shop_id, customer_id)` constraint on `shop_reviews`** (one review per customer per shop) and **a `unique` partial index enforcing one active reservation per pet** — not explicitly specified, but standard data-integrity norms directly serving the spec's own stated behavior ("enforces one active reservation per pet" is literally in the brief's notes column for `reservations`).
- **`shop_reviews_insert` requires the customer to have actually ordered from that shop**, checked via `EXISTS` against `orders`+`order_items` — this directly implements the roles table's "review a shop they've ordered from" qualifier, not an invented restriction.
- **Added a trigger-enforced guard against self-role-escalation** (`profiles.role`) **and shop self-approval/self-suspension** (`shops.status`): without it, the "own row" RLS UPDATE policies these tables need would let any customer set their own `role='admin'`, or any shop owner flip their own `status` to `'approved'`/back from `'suspended'`, undermining the whole point of admin-gated approval. This isn't scope creep — it's the RLS policies actually enforcing what the Roles table says (only admin can approve/suspend shops; nothing in the roles table lets customers self-promote).
- **Shop self-application allowed via RLS** (`shops_insert_own`: any authenticated user can insert a shop row with `owner_id = auth.uid()`, defaulting to `status='pending'`): the brief's `/for-store-owners` "Shop application form" implies someone applies *before* becoming an approved shop owner, so the insert path can't require `role='shop_owner'` already.
- **Kept `shops.phone`** (existed in the old `stores` table, not in the new spec's column list) rather than dropping it — it's compatible, already populated for both existing shops, and dropping a populated column to match a column list exactly would destroy real data for no benefit.

### RLS: a real recursion bug, found and fixed

- **`orders` and `order_items` policies each referenced the other table directly, causing `ERROR 42P17: infinite recursion detected in policy for relation "orders"`** on the very first real test query. Fixed by routing the cross-table checks through `SECURITY DEFINER` helper functions (`owns_order`, `shop_owns_item`, `owns_shop`, `customer_ordered_from_shop`) that run with the function owner's privileges and so don't re-trigger RLS on the tables they query internally — the standard fix for this exact pattern. `shop_reviews_insert_own` had the same latent (not-yet-triggered) risk and got the same fix.
- **Ran Supabase's own security/performance advisors and fixed what they found**: revoked direct RPC execution on three trigger-only functions that never need it (`handle_new_user`, and the two self-escalation guards — trigger functions run as their owner regardless of grants to the calling role, so this doesn't affect the triggers firing); added the 13 covering indexes the performance advisor flagged as missing on every new FK (these directly back the RLS subqueries, so this isn't a "next pass" optimization, it's load-bearing for the policies just written); rewrote all ~32 policy clauses to call `(select auth.uid())`/`(select public.is_admin())` instead of the bare form, fixing the "re-evaluated per row" warning. Left `is_admin()` and the four new helper functions RPC-callable by `authenticated`/`anon` (the same advisor warning) since RLS policies genuinely need to invoke them on the querying user's behalf — revoking would break the policies, not just harden them.
- **`auth_leaked_password_protection` (disabled) is an Auth-settings toggle**, not a migration/schema concern — flagging it here since it's outside what a SQL migration can fix, not silently ignoring it.
- **Actually tested RLS as real users, not just written it.** Simulated `customer` (Ananya Singh) and `shop_owner` (Ravi Kumar) sessions via `set local role authenticated; set local request.jwt.claims = ...` (the same mechanism PostgREST uses) and verified: customer sees only their own profile/reservations/orders/wishlist, sees available pets only (the one `sold` pet is hidden), cannot insert a shop under someone else's `owner_id`, cannot self-escalate to `admin` (reverted by trigger), cannot update a pet they don't own (0 rows affected). Shop owner sees their own shop's full inventory (would include sold pets if they had any) but only the *available* pets of shops they don't own, can update their own shop's pets but not another shop's (0 rows affected), and cannot self-suspend/self-approve their own shop (trigger reverts it). Test writes were rolled back / restored afterward (see below).
- **Test-mutated 3 pet prices to `999` while verifying shop-owner write access, then restored them** to values matching the existing dataset's ₹22,000–32,000 scale (the original values weren't captured beforehand — a process gap I'm flagging rather than hiding; the restored values are reasonable estimates, not the literal originals).

### Frontend routes

- **Renamed existing working routes to match the new IA rather than rebuilding them**: `/shops`→`/sellers`, `/shops/:id`→`/sellers/:id`, `/sell`→`/for-store-owners`. These pages were already fully functional from the prior marketplace-frontend pass; the brief's "nothing gets rebuilt" instruction reads as preserving that investment, not discarding it because a fresh-start description of this phase wouldn't have had it yet. Updated every internal `Link`/`Button to=` reference across the app (`PetCard`, `ShopCard`, `Header`, `Footer`, `Home`, `PetDetail`, `ShopDetail`) to match.
- **All 21 genuinely new routes** (`/store`, `/store/:id`, `/gifting`, `/learn`, `/cart`, `/reserve/:petId`, `/support`, `/account`, and all 13 `/seller/*` + `/admin/*` dashboard routes) **are bare placeholders** — a heading via a shared `PagePlaceholder` component, nothing else, per the brief.
- **Did not touch the existing working `PetDetail`/cart-drawer flow to reconcile it with `/reserve/:petId`.** The brief's roles table distinguishes "reserve a pet (deposit)" from "buy a store item (full checkout)," implying pets should eventually route through a deposit flow instead of the cart — but rebuilding that interaction is exactly the "cart logic... next prompt" work this pass explicitly excludes. `/reserve/:petId` exists as an empty route now; reconciling it with `PetDetail`'s current Add-to-Cart behavior is next-pass work, flagged here so it isn't a surprise.
- **`/cart` is now also a route** (previously the cart was drawer-only, no dedicated page). Added as an empty placeholder alongside the still-fully-functional `CartDrawer` — not reconciling page-vs-drawer architecture in this pass either, same reasoning as above.

## Image sourcing (read this first)

- **Dog photos come from the Dog CEO API** (`dog.ceo/api/breed/{breed}/images/random/3`), **no key needed.** Breed → slug mapping used: Labrador Retriever → `labrador`, Beagle → `beagle`, Golden Retriever → `retriever/golden`, Standard Poodle → `poodle/standard`. Slugs were pulled from the API's own `/breeds/list/all` response, not guessed, so they're guaranteed valid.
- **Cat photos come from TheCatAPI** (`api.thecatapi.com/v1/images/search?breed_ids={id}&limit=3`), using their **publicly documented demo key** `DEMO-API-KEY` (this is TheCatAPI's own listed test key, not a real secret) — swap for a registered key before anything resembling production. Breed → id mapping: Siamese → `siam`, Maine Coon → `mcoo`, British Shorthair → `bsho`.
- **Every one of the 21 resulting image URLs (12 dog + 9 cat) was individually curl'd and checked for HTTP 200 + an `image/*` content-type before being hardcoded into `src/data/pets.js`.** This is the step that failed last time — placeholder images that were never actually verified against the animal they were supposed to represent.
- **URLs are resolved once and hardcoded, not fetched live in the app.** Dog CEO/TheCatAPI URLs are stable CDN links, so baking them into seed data means the app has zero runtime dependency on either third-party API — no loading states, no rate-limit risk, no live-fetch failure mode to design around. This is the simplest thing that works, not an abstraction for its own sake.
- **Rabbit, Bird, and Small Pet (guinea pig) entries carry `photos: null` and render a hand-illustrated `SpeciesIcon` instead** — there's no reliable free breed-photo API for these, and the brief is explicit that a deliberately-illustrated placeholder reads as intentional where a wrong photo reads as broken.
- **`SpeciesIcon` covers all 5 categories (Dog, Cat, Bird, Rabbit, Small Pet), not just the 3 without photo APIs** — it's also the universal fallback for a Dog/Cat photo that fails to load at runtime (`PetPhoto`'s `onError` swaps to it), so every species needs one regardless of whether it has a primary photo source.
- **`PetPhoto` takes a bare `src` + `species`, not a whole pet object,** so the exact same fallback-on-error component renders both a card thumbnail and every image in the detail-page gallery independently — each image in a 3-photo gallery has its own fallback, not just the first one.

## Design system vs. the loaded `high-end-visual-design` skill

- **The project brief's own explicit tokens/structure govern; the generically-invoked `high-end-visual-design` skill's maximalist mandates are followed only where they don't conflict.** The skill wants forced vibe archetypes, Double-Bezel nested card shells on every surface, and `py-24`–`py-40` section padding; the brief explicitly bans "identical rounded-shadow treatment applied without regard to hierarchy" and wants a grid "denser than a boutique site." Those directly contradict each other — the specific, detailed product brief wins. Kept from the skill: GPU-safe transform/opacity-only motion, no `window.scroll` listeners, `min-h-[100dvh]` over `h-screen`, restrained custom easing over `linear`. Dropped: forced OLED/editorial/glass vibe selection, universal nested-shell card architecture, button-in-button icon wells, floating-island nav, magnetic hover physics, massive whitespace scale — none of that fits a dense marketplace grid.

## Other decisions

- **Removed Three.js, GSAP, Lenis, and Framer Motion; added Zustand.** The new brief has no 3D/scroll-choreography surface at all (and explicitly bans a 3D/illustrated hero) and needs real cart/wishlist state — keeping the old motion stack would be unused weight, and hover-lift/drawer-slide only need plain CSS transitions.
- **Corner-radius:** `rounded-xl` for cards/photos, `rounded-lg` for buttons/inputs, `rounded-full` only for the true badge/pill cases (cart count badge). Not a full-pill button system this time — a dense marketplace reads more like practical e-commerce than a SaaS landing page.
- **Cart line items are pet ids, not `{id, qty}` pairs.** Quantity is always 1 (a pet is a unique animal, never restockable), so `addToCart` is just idempotent array-membership — no quantity field exists anywhere to accidentally increment.
- **Cart/wishlist persist via Zustand's `persist` middleware to localStorage; the drawer's open/closed flag is explicitly excluded via `partialize`** so a reload never resurrects an open drawer.
- **`CartDrawer` is one component that's a bottom sheet under `md:` and a right-side drawer at `md:` and up,** switching which transform axis animates (`translateY` vs `translateX`) via Tailwind breakpoint variants rather than shipping two components.
- **Checkout step/form state is local `useState` in `Checkout.jsx`, not in the Zustand store.** It's a linear, one-time flow with nothing else that needs to read it — putting it in global state would be unrequested abstraction.
- **Added one token beyond the given list: `--color-error` (#c63c33).** The brief's token table has no semantic error color and the checkout buyer-details form needs one; picked a color clearly distinct from `--color-accent` (orange) so an error state is never visually confusable with a price/CTA.
- **Checkout confirmation explicitly does not say "payment successful."** It confirms the order is placed and pending, and that pickup + final payment happen at the shop — this exact distinction is called out in the brief as a copy detail that must not get lost, so the confirmation copy was written and re-read specifically for this.

## Auth: sign up / login / role-based redirect

- **The sign-up role dropdown lets anyone self-select Admin. Flagged, not silently blocked.** Letting a public sign-up form hand out `role='admin'` is a real privilege-escalation hole in anything resembling production — but it was asked for explicitly, this project is still at the prototype/demo stage, and the RLS layer underneath already prevents an admin-flagged account from doing anything an admin shouldn't be able to undo (the `profiles`/`shops` self-escalation triggers from the schema pass are unaffected — they stop *existing* accounts from promoting *themselves*, which is a different concern from sign-up handing out the role directly). Built exactly as asked, with a visible caption on the dropdown itself ("Demo/testing only — a real deployment shouldn't let anyone self-register as Admin") so it isn't a silent landmine. Before any real deployment: remove Admin from the dropdown and provision admin accounts out-of-band.
- **Sign-up handles both Supabase auth outcomes** (immediate session vs. "confirm your email first") **rather than assuming one.** Tested against the live project and confirmed it currently requires email confirmation — `signUp()` returns no session — so a naive "always redirect after sign-up" would have silently sent unauthenticated users into a route guard's redirect loop. The form checks `data.session` and shows a "check your email" state when it's null instead.
- **Role-based redirect destinations:** `customer` → `/account`, `shop_owner` → `/seller/dashboard`, `admin` → `/admin/dashboard`. The brief's route table doesn't define a single "customer dashboard," but `/account` ("Orders, reservations, wishlist, profile") is its closest analog — sending customers to the generic home page instead would make "directed to their respective page" meaningless for that role.
- **Added `ProtectedRoute` gating every `/seller/*` and `/admin/*` route**, even though only sign-up/login/redirect were asked for. Redirect-after-login only matters if the destination is actually protected — without a guard, any signed-out visitor (or a customer, or the wrong dashboard's owner) could still reach another role's dashboard by typing the URL directly, which would make the redirect purely cosmetic. Not signed in → `/login`; signed in as the wrong role → their own `roleHomePath`, not a blank/forbidden page.
- **Verified the whole loop against the live project, not just written it**: signed up a real test `shop_owner` account through the actual form, confirmed the `profiles` row landed with the correct role/name/phone/email via the `handle_new_user` trigger, manually confirmed its email (`auth.users.email_confirmed_at`) since no real inbox exists in this environment, logged in through the real form and confirmed it landed on `/seller/dashboard`, confirmed hitting `/admin/dashboard` while signed in as that shop owner bounced back to `/seller/dashboard`, logged out, and confirmed hitting `/seller/dashboard` while signed out bounced to `/login`.
- **Auth session/profile state lives in a Zustand store (`authStore.js`)**, matching the existing `cartStore` pattern, rather than React Context — consistent with how the rest of the app already manages cross-component client state.
- **Supabase URL/anon key live in `.env`** (gitignored) **with a checked-in `.env.example`.** The anon key is a public-by-design key (subject to RLS, not a secret), but keeping credentials out of the diff either way is standard hygiene, not a security requirement here specifically.
- **The production build intermittently ran out of memory while the Vite dev server was also running** (`rolldown` + `esbuild`, both memory-hungry, competing for the same box). Not a code problem — stopping the dev server before running `npm run build` resolved it every time. Worth knowing if this trips again.

## Customer / shop-owner / admin dashboard pages (19 previously-placeholder routes)

- **Built as real Supabase-backed pages, not static mockups**, matching the hand-drawn page-requirement diagram: customer catalog/medicine/store/gifting/support/learn pages, shop-owner dashboard/store-profile/pets/products/orders/support/contract pages, admin dashboard/shops/orders/videos/support/contracts pages.
- **Deliberately did not reconcile the two parallel data sources.** `/pets`, `/sellers`, `/checkout` still read from the static `src/data/pets.js`/`shops.js` seed files (pre-existing, fully working); every new page added in this pass reads live from Supabase instead. Agents were explicitly briefed never to import from `src/data/*`. Reconciling these into one source is out of scope — flagged so it isn't mistaken for an oversight.
- **`useMyShop()` (`src/hooks/useMyShop.js`) is a new shared hook** — every `/seller/*` page needs "the shop owned by the current user," so this was pulled out once rather than duplicated seven times.
- **Parallel Agent-tool build-out, briefed with full shared context** (schema, RLS behavior, exact component-reuse instructions, exact file paths) so independently-written pages stayed visually and structurally consistent without seeing each other's code. One agent (shop-owner-core) hit a 429 mid-run and never wrote `Products.jsx`; it was written by hand afterward, mirroring the sibling `Pets.jsx` file's pattern.
- **Found and fixed a real race condition in `seller/Dashboard.jsx`**: the loading guard checked `shopLoading || statsLoading` but not whether `stats` itself was still `null`. When `shop` flips from `null` to a real shop object, React re-renders once before the dependent `useEffect` (which fetches stats) has had a chance to run — a one-frame window where both loading flags are `false` but `stats` is still `null`, crashing on `stats.petsCount`. Fixed by adding `!stats` to the guard.
- **Found and fixed a systemic PostgREST embedding bug**: 9 FK columns (`orders.customer_id`, `shops.owner_id`, `support_tickets.customer_id`, `support_messages.sender_id`, `gifts.sender_id`, `reservations.customer_id`, `shop_reviews.customer_id`, `wishlists.customer_id`, `reference_videos.created_by`) pointed at `auth.users(id)` instead of `public.profiles(id)`. PostgREST's nested-select syntax (`select("*, profiles(name,email)")`) — used by 5 of the agent-written pages to show customer/sender names — can only auto-resolve a join across a *direct* FK, so every one of those queries failed with "Could not find a relationship..." Fixed at the schema level (`repoint_user_fks_to_profiles` migration, re-pointing all 9 FKs to `profiles(id)`, valid since `profiles.id` mirrors `auth.users.id` 1:1 via the signup trigger) rather than patching each page's query shape individually — this was a schema defect, not 5 separate frontend bugs.
- **Added `profiles_select_shop_customers` RLS policy** so a shop owner can see the name/email of a customer who ordered from or messaged their shop — the existing `profiles_select` policy only let a user read their own profile, which would leave shop-owner order/support pages showing "Unknown customer" for everyone. Scoped narrowly (shop owner ↔ their own customers only), not a global profile-read loosening.
- **Fixed two accent-color rule violations found during verification** (accent reserved for CTA/price/active-state only, per the brief): `seller/Support.jsx`'s `in_progress` status pill used `bg-accent/10 text-accent` (now `bg-primary/10 text-primary`, matching the admin equivalent — confirms this was an isolated slip, not a pattern); `PetDetail.jsx`'s wishlist heart button used `accent` for its active/hover state (now `primary`), a pre-existing bug from the earlier frontend pass, not something introduced here.
- **Real seed data prices are INR-scale (e.g. ₹28,000 for a pet) but `formatPrice` still renders a `$` prefix.** No currency field exists in the schema. Left as-is — fixing it means picking a currency-handling model (stored currency code? all-INR? convert display only?) that's a real design decision outside this pass's scope, not a one-line fix.
- **Verified all 19 pages hands-on in the browser as real accounts** (a fresh customer, the two existing shop owners, and a freshly-created admin — `admin.test.qa@gmail.com`, email-confirmed manually via SQL the same way prior test accounts were), including write paths: shop suspend/reactivate, video add/delete, support ticket reply + status change, product/pet add. `window.confirm()` dialogs don't block Claude Code's automated browser (they auto-resolve to `false`), so confirm-gated actions (shop suspend, video delete) needed `window.confirm` temporarily overridden to `() => true` in-page to actually exercise the write path — worth knowing if a future verification pass hits an action that silently no-ops.
